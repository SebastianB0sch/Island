# Card effect coverage

Generated by `python Tools/effects/report_coverage.py`. The manifest is the source of truth: one row per card in `cards.json`.

## Status model

| Status | Meaning |
| --- | --- |
| `scripted` | A data script exists (`Effects/scripts/<id>.json`), or the card is part of the 137-card regression baseline and has a verified name handler in `DADuelEngine.cpp`. |
| `vanilla` | No standalone effect to script. Normal Monsters use generic rules; effect-free Fusions/Rituals use `fusions.json` / `rituals.json`; specific Ritual Spell procedures are owned by `rituals.json`; summoning-restriction-only monsters have no executable effect. |
| `pending` | Effect text exists, but the whole printed effect is not covered by a validated data script or verified engine handler. `pending_reason_code` names the blocking runtime capability. |
| `unsupported` | The card cannot be represented yet. This is always an explicit release blocker. |

## Method

- **253 validated card scripts** exist: 10 hand-authored examples and 243 generated by `Tools/effects/generate_scripts.py`.
- The generator uses whole-card patterns from `Tools/effects/effect_patterns.py`. A card is scripted only when every printed clause is represented; otherwise it stays `pending` with a reason code.
- `python Tools/effects/validate_effects.py` checks the JSON Schema, per-card source text, manifest hashes, script ids, fusion/ritual accounting and usage legality.

## Runtime caveats in this batch

- **Generic Equip/Field activation persistence.** The 40 `equip_continuous` / `field_continuous` scripts are schema-valid, but `FDuelEngine::ActivateSpell` still decides whether a card stays on the field with the legacy `IsEquipName` / `IsFieldSpellName` lists. Until A04 generalises `bStays`, these cards only apply when the card is already placed/attached; activating them from the hand sends them to the Graveyard after resolution.
- **Self-trigger source binding.** Field-scanned triggers such as `on_battle_destroy`, `on_sent_to_graveyard`, `on_tribute_summon`, `on_position_change` and `on_summon` still consider other card ids on the field. The new attacker hooks use the supported `battle_involving_self` predicate where possible, but A04 still needs strict self-trigger binding (or an `event_source_is_self` condition) for the remaining cases.

## How Tier 0 was identified

The current four decks in `Content/Data/decks.json` contain exactly **137 unique cards**. That union is the regression baseline and is assigned Tier 0. Of those 137, **110 names occur verbatim in `DADuelEngine.cpp`** (109 effect-bearing cards plus Harpie Lady, which is a Normal Monster); the other **27** are Normal Monsters or the effect-free Fusion Monster 319, handled by generic rules and `fusions.json`. The manifest therefore credits 109 `engine_cpp` scripts and 28 `vanilla` cards, with zero pending Tier 0 cards.

This is an attestation of the current C++ baseline, not a claim that those 109 cards already have data scripts. When A04 ports the handlers into the effect runtime, each one must move from `implementation=engine_cpp` to `implementation=data_script` without changing behaviour.
